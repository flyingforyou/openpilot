### 분석할 때 주의

- **`live.jsonl`의 `values`를 그대로 쓰지 말 것.** 앞 209줄(15:40 이전)은 고치기 전 디코더로 기록돼서
  전류가 -984 A, 남은 에너지가 완충보다 큼. 같은 줄의 `raw`를 지금 디코더로 다시 돌리면 된다:

  ```python
  from openpilot.system.btobd import tesla_sx as t
  s = t.TeslaSXState()
  for line in open('live.jsonl'):
    r = json.loads(line)
    for fid, h in (r.get('raw') or {}).items():
      s.feed(int(fid, 16), bytes.fromhex(h.replace(' ', '')), r['t'])
    # s.values 가 그 시점의 값
  ```
- `raw`는 ID별 **마지막** 프레임만 담는다(전체 스트림 아님). 전체 스트림은 캡처 파일.
- `live.jsonl` 간격은 약 3.7초(데몬이 ID를 하나씩 도는 한 바퀴). 35~121초 공백은 점검·UDS·캡처 중
  데몬이 묶인 시간이라 정상.

## 동글

ELM327 v1.5 클론. `ATCSM1`(CAN 무음 감시) **미지원**, `ATCRA` 와일드카드(`0XX`)는 지원.
진단 커넥터의 프로토콜 6(CAN 11비트 500k)에서 배터리 메시지(0x102/0x302/0x382/0x6F2)와 조향각(0x00E)이 들림.

## 이 차에서 확인한 디코딩 (wk057 2016 문서와 다른 점)

| 메시지 | wk057 | 이 차 | 근거 |
|---|---|---|---|
| 0x382 에너지 | 10비트 필드 | **11비트 필드** | 10비트로 읽으면 남은 75.6 kWh > 완충 72.9. 11비트: 남은/예상/이상 = 37.8/38.4/37.9, 버퍼 6.0, 37.8/72.9 = 51.9% = 같은 시점 socUI |

| 계기판 SOC | — | `(남은 - 버퍼) / (완충 - 버퍼)` | 대시 45% ↔ socUI 49% → (0.49·72.9−6.0)/(72.9−6.0) = 44.4%. 수정 후 페이지 49.0% = 대시 49% 확인 |

전류 부호: 양수 = 팩으로 들어감(wk057과 같음). 이날 계속 +15.2~16.0 A, SOC 49.0 → 50.5%(계기판 기준)로
올라서 충전 중이었음이 확인됨.

이날 끝 시점 값: 완충(공칭) 72.9 kWh, 버퍼 6.0 kWh, 셀 3.8162~3.8363 V (편차 20 mV), 모듈 온도 22.1~23.9 °C,
팩 368.5 V.

디코더는 0x382 레이아웃을 프레임마다 판별(세 남은 값이 서로 맞고 팩 안에 드는 쪽)하고, 0x102 오프셋은
+600 A를 넘는 값이 한 번이라도 보이면 그 차는 오프셋 차로 고정한다. 그래서 wk057 예제 프레임도 그대로 맞는다.

## 캡처

- 고치기 전: 필터 없는 `ATMA`가 0.16초 만에 동글 버퍼를 넘치게 했고, ELM327은 `BUFFER FULL`에서 감시를
  멈춘다 → 30초 캡처에 21프레임.
- 고친 후: 수신 필터를 ID 첫 자리 8구간(`0XX`..`7XX`)으로 돌려가며 1.5초씩 듣고, 넘치면 `ATMA`를 다시 건다.
  120초 → 13,676프레임, ID 216개, 0~120초 고르게. 여전히 `bufferFull: true`(넘침은 있었지만 이제 멈추지 않음).
- **정정 (나중에 확인): 이 캡처는 구간 필터가 실제로 걸리지 않았다.** 동글이 `ATCRA0XX`에 `OK`라고 답하고는
  와일드카드를 무시해서, 0.5초마다 0~7 모든 구간의 ID가 다 들어 있다. 즉 사실상 필터 없는 캡처 + 넘침 후 재시작.
  초당 114프레임만 남았고(0x102 하나가 100 Hz인데 120초에 1,075개 ≈ 9 Hz) 나머지는 넘침으로 빠졌다.
  → **이 캡처의 개수/Hz는 실제 송신 주기가 아니라 동글이 건져낸 표본**이다. ID 목록과 프레임 내용은 유효.
- 정확한 ID 하나(`ATCRA6F2` 등)는 이 동글에서 제대로 걸린다: 데몬의 셀 스윕이 1.2초에 0x6F2 mux를 약 11개씩
  연속으로 받음(0x6F2는 mux 0→31을 약 9 Hz로 순서대로 보냄).
- 수정 후 캡처는 구간마다 범위 밖 ID가 얼마나 새는지 직접 세서, 새면 `ATCF/ATCM`(필터+마스크)로, 그것도 새면
  필터 없이로 내려가고, meta `filter`에 실제로 걸린 방식(`cra`/`mask`/`null`)을 남긴다. 이 동글에서
  `ATCF/ATCM`이 먹는지는 아직 실차 미확인.
- 1바이트 프레임(0x408/0x40E/0x20D/0x41E)은 원래 1바이트 메시지(두 캡처에서 같은 값). 해석 못 한 줄 429개는 동글이
  넘칠 때의 잡음으로 추정 — 원문은 캡처에 저장되지 않음.
- 이 캡처 meta의 `"dongle": "STOPPED"`는 버그였음(아래). 실제는 ELM327 v1.5.

## UDS / OBD — 이 포트에서는 응답 없음

차로 보낸 건 읽기 전용 7건이 전부(`uds_audit.jsonl`):

| 대상 | 요청 ID | 요청 | 응답 필터 | 결과 |
|---|---|---|---|---|
| IC | 0x64C | 22 F190 (VIN) | 0x654 | NO DATA |
| DAS | 0x649 | 22 F190 | 0x651 | NO DATA |
| IC / DAS | 0x64C / 0x649 | 3E 00 (TesterPresent) | 6XX | 없음 |
| IC / DAS | 0x64C / 0x649 | 3E 00 | XXX (전체) | 없음 — 원문 `NO DATA` |
| OBD-II 기능 주소 | 0x7DF | 09 00 | 7XX | 없음 — 원문 `NO DATA` |

- 요청 ID 0x64C/0x649 출처: talas9/tesla_can_signals ModelS CH 버스 파일(`UDS_icRequest`, `UDS_dasRequest`, 송신자 `gtw`/`tool`). 응답 ID는 그 파일에 없음.
- `NO DATA`는 `CAN ERROR`가 아님 → 요청 프레임은 버스에서 ACK됨. 수신 필터를 전부 열어도 답이 없으니
  응답 ID 추정 문제도 아님.
- 추정(미확인): 진단 요청은 게이트웨이가 중계해야 모듈에 닿고, 이 포트에서 직접 보낸 요청은 Tesla 진단툴
  인증 없이 중계되지 않는다. 2016년식이라 표준 OBD-II 의무 대상도 아님.
- 그래서 추측성 주소로 더 보내지 않고 중단. 초안 프로파일은 미검증 상태로 남겨 둠.

## 디코딩 오류 (나중에 확인)

- 0x102 바이트 6~7 `FC 1F` → 11비트 0x7FC = 204.4 °C가 모든 프레임에서 고정. 온도가 아니라 "값 없음" 코드.
  /diag는 이걸 음극 단자 온도로 표시했고, 건강 점검은 "단자가 모듈보다 180 °C 뜨거움 → 나쁨"으로 판정했음(오경보).
  이제 0x7F0 이상은 값을 내지 않는다.
